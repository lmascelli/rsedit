NAME
    modes - what a buffer is being edited as

DESCRIPTION
    Every buffer has one major mode. It decides three things: how the text is
    coloured, which keys mean something other than what they usually mean, and
    what counts as a comment.

    C-h M says what the current buffer's mode is and what it does.

WHICH MODE A BUFFER GETS
    From its file's name. A .rs file gives you rust-mode; .c, .h, .cpp, .hpp,
    .cc, .cxx and .hxx give cpp-mode; .lisp and .risp give risp-mode, which is
    this editor's own Lisp. Anything else is fundamental-mode, which colours
    nothing and takes no keys of its own.

    A buffer that is not a file gets the mode whatever made it asked for: a
    directory listing is dired-mode, a compilation's output is
    compilation-mode, a manual page is manpage-mode.

WHAT COLOURING IS
    A list of patterns over the text, each saying "this shape is a keyword"
    or "this shape is a string". It is not a parser: a mode can say that a
    word in a list is a keyword and cannot say anything about what the code
    means.

    That is a deliberate limit, and the thing that fills the gap is an
    *overlay* -- a face on one particular span, put there by something that
    knows why. A search marks its matches that way, and so does a
    compilation's current complaint. See `overlays'.

    Colour arrives a chunk at a time on a background thread, so a large file
    opens as plain text and fills in rather than making you wait.

MODES THAT SHIP
        fundamental-mode    no colouring, no keys of its own
        rust-mode           .rs
        cpp-mode            .c, .h, .cpp, .hpp, .cc, .cxx, .hxx
        risp-mode           .lisp, .risp -- this editor's own Lisp
        dired-mode          a directory listing
        compilation-mode    a build's output
        shell-output-mode   a command's output
        occur-mode          a list of matches
        manpage-mode        a manual page
        help-mode           an answer from the help system
        buffer-list-mode    the list of buffers
        minibuffer-mode     a prompt
        isearch-mode        a search in progress
        completion-mode     the strip of candidates
        theme-list-mode     the list of themes
        backtrace-mode      where an error came from

    Each is a .lisp file you can read, and taking one out of your
    configuration removes exactly that feature.

MODE KEYS
    A mode's keys are consulted before the global ones, so a listing can use
    plain letters. Nearly all of them agree on four:

        n  p            down and up a line
        q               put this away
        g               build it again, where that means anything

    A key the mode does not bind falls through to the global map, which is why
    C-x C-f works in a directory listing.

HOOKS
    Hooks are functions called without arguments, in registration order:

        (add-hook 'rust-mode "post-command-hook" 'my-function)

    nil instead of a mode name means every mode. Each event runs its
    mode-specific callbacks before global callbacks. add-hook ignores
    duplicate registrations in the same scope; remove-hook takes the same
    three arguments. Errors are logged and do not prevent the remaining
    callbacks from running.

    pre-command-hook runs before a command; post-command-hook after it.
    post-self-insert-hook runs after a character is typed, for auto-pairing.

BUFFER LIFECYCLE
    Every newly allocated buffer runs these events, in this order:

        buffer-created-hook             Buffer and major mode are available.
        major-mode-hook                 Setup for that major mode.
        after-change-major-mode-hook    General setup after mode callbacks.
        find-file-hook                  File visits only, including new files.

    Callbacks see the new buffer as current. Creating a hidden buffer does not
    display it or change window focus. File text and path are already
    available for file visits; producers of generated buffers may populate
    them later. Re-selecting, re-opening or buffer-create on an existing
    buffer does not run initialization again. A replacement *scratch* after
    closing the last buffer is a new allocation and receives these hooks too.

        (defun my-rust-setup () (buffer-put 'my-setting 4))
        (add-hook 'rust-mode "major-mode-hook" 'my-rust-setup)
        (add-hook nil "find-file-hook" 'my-file-setup)

    (set-major-mode 'rust-mode) selects a registered mode for the current
    buffer, invalidates its syntax caches, then runs major-mode-hook and
    after-change-major-mode-hook. Selecting the same mode is a no-op.
    write-file uses this path when a new filename selects a different mode.
    After a successful write-file changes the visited path, it also runs
    after-set-visited-file-name-hook, with the final name and mode available.

    This follows Emacs's distinction between mode setup and file visits.
    rsedit uses (add-hook MODE "major-mode-hook" FUNCTION) where Emacs would
    use a variable such as rust-mode-hook. It matches exact mode names; there
    is no derived-mode inheritance or buffer-local hook variable. Unlike
    Emacs, set-major-mode retains buffer-local metadata. The initial *scratch*
    predates init.lisp; use a globalized mode's refresh to cover existing
    buffers.

    Vim uses these generic events to implement global-vim-mode and selection
    by major mode in Risp. A globalized mode applies buffer-local keymaps to
    eligible buffers, keeping minibuffers and service buffer commands usable.

WRITING ONE
    A mode is `make-mode', some `add-syntax-rule' calls, some `define-key'
    calls, and an `add-auto-mode' saying which file names it claims.
    rust-mode.lisp is a hundred and thirty lines of it and is the one to copy.
