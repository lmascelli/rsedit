NAME
    modes - what a buffer is being edited as

SYNOPSIS
    (add-auto-mode PATTERN MODE)
    (add-hook MODE HOOK FUNCTION)
    (remove-hook MODE HOOK FUNCTION)
    (risp-refresh-vocabulary)
    risp-special-forms
    risp-constants
    rust-keywords
    rust-constants
    rust-types
    (cpp-add-raw-string-delimiter DELIMITER)
    (bash-add-heredoc-delimiter DELIMITER)
    c-keywords
    c-constants
    c-types
    cpp-keywords
    cpp-constants
    cpp-types
    python-keywords
    python-constants
    python-builtins
    python-types
    toml-constants
    bash-keywords
    bash-builtins

DESCRIPTION
    Every buffer has one major mode, and the mode says what the buffer is
    edited as: how its text is coloured, what its brackets, strings and
    comments are, how Tab indents a line, which words C-M-i offers, and
    which keys do something of their own in it. The status line shows the
    mode's name, and C-h M describes it, with the keys it binds.

    A file gets its mode from its name, and a buffer that is not a file --
    a directory listing, a manual page, a list of matches -- from whatever
    made it. `set-major-mode' gives the current buffer another, as the
    `buffers' page says. Making a mode of your own is `writing-modes'.

WHICH MODE A FILE GETS
        rust-mode           .rs
        c-mode              .c .h
        cpp-mode            .cpp .hpp .cc .hh .cxx .hxx .c++ .h++ .C .H
                            .ipp .tpp .ixx .cppm
        risp-mode           .lisp .risp
        python-mode         .py .pyw .pyi
        toml-mode           .toml, and Cargo.lock
        bash-mode           .sh .bash .bashrc .bash_profile .bash_login
                            .bash_logout .profile
        fundamental-mode    any other name

    `add-auto-mode' adds a name to these. PATTERN is a regular expression
    matched against the file's whole path, so it can name a directory as
    well as an extension. The first pattern declared that matches is the
    one that counts, and the modules declare theirs as they load: a pattern
    of yours that takes a name from one of them goes at the top of
    init.lisp, before the modules. MODE need not exist yet.

    The mode is chosen when the file is opened, and again when C-x C-w
    writes the buffer under a name that another pattern claims. A name no
    pattern claims leaves the mode as it was.

    A .h file is C. To open headers as C++, put this at the top of
    init.lisp, before the modules, since the first pattern declared wins:

        (add-auto-mode "\\.h$" 'cpp-mode)

    A script without a recognized extension can be switched explicitly:

        (set-major-mode 'bash-mode)

MODES THAT SHIP
        fundamental-mode    plain text: no colours, no keys of its own
        rust-mode           Rust
        c-mode              C source and headers
        cpp-mode            C++ source, headers and module interfaces
        python-mode         Python source and type stubs
        toml-mode           TOML configuration and Cargo.lock
        bash-mode           Bash and Bourne-style shell scripts
        risp-mode           this editor's own Lisp
        dired-mode          a directory listing
        buffer-list-mode    the list of buffers
        compilation-mode    the output of a build
        occur-mode          a list of matches
        shell-output-mode   what a shell command printed
        help-mode           an answer from C-h
        manpage-mode        a page of this manual
        theme-list-mode     the list of themes
        backtrace-mode      where an error came from
        minibuffer-mode     a prompt
        isearch-mode        the prompt of an incremental search
        completion-mode     the strip of candidates

    In the buffers the editor makes to show you something -- the listings,
    the help, the manual -- n and p go down and up, a line at a time or in a
    build's output a complaint at a time, and q puts the buffer away. g
    reads dired, the buffer list and the theme list again, and runs a build
    again. A key a mode does not bind does what it does everywhere else, so
    C-x C-f works in a directory listing.

THE LANGUAGES
    Each language mode colours the keywords, strings and comments of its
    language, and tells the editor its brackets, strings and comments,
    which C-M-f and M-; go by. Each colours more of its own:

        rust-mode     numbers, types, functions, doc comments, attributes
        c-mode        numbers, types, functions, doc comments, the
                      preprocessor
        cpp-mode      what c-mode does, and attributes
        python-mode   numbers, types, functions, decorators
        risp-mode     numbers, functions and macros, the names defined
        toml-mode     numbers, dates, keys, table headers
        bash-mode     builtins, variables, functions, heredocs

    All of them but rust-mode indent as their language does, as the
    `indentation' page says; in rust-mode Tab matches the line above.

    Their words are lists you can read: `rust-keywords', `rust-constants'
    and `rust-types'; `c-keywords', `c-constants' and `c-types';
    `cpp-keywords', `cpp-constants' and `cpp-types'; `python-keywords',
    `python-constants', `python-builtins' and `python-types';
    `toml-constants'; `bash-keywords' and `bash-builtins';
    `risp-special-forms' and `risp-constants'. C-M-i offers them as
    keywords. The colouring and what C-M-i offers are both made from the
    lists when the module loads, so changing a list afterwards changes
    neither.

    risp-mode does not list the functions and macros it colours: it asks
    the interpreter, which knows every one there is, yours included. It
    asks when it loads, so a function defined since is coloured once M-x
    risp-refresh-vocabulary has asked again. C-M-i asks every time, and
    needs nothing.

LANGUAGE CONFIGURATION
    An existing init.lisp is not rewritten by an editor upgrade. Load the
    modules there; each loads the ones it needs first:

        (require 'cc-mode)
        (require 'python-mode)
        (require 'toml-mode)
        (require 'bash-mode)

    C/C++ include C11/C23 and modern C++ vocabulary, preprocessor directives,
    attributes, numeric suffixes and character literals. C++ raw strings
    with an empty tag or raw, tag, json, xml, sql and glsl are recognized.
    Register another literal delimiter in both engines with:

        (cpp-add-raw-string-delimiter "shader")

    Bash heredocs ending in EOF, EOT and END are coloured across lines.
    Another literal marker can be added with:

        (bash-add-heredoc-delimiter "SCRIPT")

    The Bash indenter recognizes literal word heredoc markers independently
    of this colouring registration, including quoted markers and <<-.
    See `indentation' for the language-specific rules and their limits.

HOOKS
    A hook is a list of functions the editor calls at a moment of its own,
    named by a string:

        pre-command-hook        before every command
        post-command-hook       after every command that did not fail
        post-self-insert-hook   after a key that types itself, before
                                post-command-hook; not after a paste
        buffer-created-hook     a buffer has just been made
        major-mode-hook         a buffer has its mode: it has just been
                                made, or its mode has just changed
        after-change-major-mode-hook
                                straight after major-mode-hook
        find-file-hook          a file has been opened in a new buffer,
                                after those three
        after-set-visited-file-name-hook
                                C-x C-w has written the buffer to a file
                                it was not visiting
        after-close-hook        a buffer has been closed

    (add-hook 'rust-mode "find-file-hook" 'my-rust-setup) calls the function
    my-rust-setup, with no arguments, when a Rust file is opened; nil in
    place of the mode calls it whatever the mode. FUNCTION is the name of a
    function: a lambda is refused. The functions run in the order they were
    added, the mode's own before those for every mode, with the buffer
    concerned current; after-close-hook runs those of the closed buffer's
    mode, once it has gone. A function added twice runs once.

    `remove-hook' takes the same arguments: with a mode it takes the
    function off that mode's hook, and with nil off the one for every mode.
    A function that fails is reported in the log, and the others still run.
    The first *scratch* is made before init.lisp is read, so the hooks of
    a new buffer that init.lisp adds do not run for it.

LIMITS
    Loading a mode's file again makes the mode again, empty: the keys and
    hooks other files gave it go, electric-pair's among them.

    Colouring uses regular expressions, not a compiler or a full parser.
    Python f-strings and shell strings are coloured uniformly, including
    interpolation. Python match and case are treated as keywords everywhere.
    Arbitrary C++ raw-string tags and Bash heredoc markers need the explicit
    colouring registrations above: the regexp engine has no backreferences.
    The Bash structural scanner treats # as a comment opener even inside an
    unquoted word or parameter expansion; the indenter has its own shell
    lexer and does not have that limitation. Shebangs are not mode selectors.

EXAMPLES
    Open .ino files as C++, at the top of init.lisp:

        (add-auto-mode "\\.ino$" 'cpp-mode)

    Say which file has been opened, whatever its mode:

        (defun my-opened () (message "Opened %s" (current-buffer)))
        (add-hook nil "find-file-hook" 'my-opened)

    And stop saying it:

        (remove-hook nil "find-file-hook" 'my-opened)

    Colour the Lisp functions defined since risp-mode loaded:

        (risp-refresh-vocabulary)

    How many keywords rust-mode knows:

        (length rust-keywords)
