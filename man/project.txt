NAME
    project - the tree a file belongs to, and working on all of it

SYNOPSIS

DESCRIPTION
    A project is a directory and everything under it: a repository, a
    crate, the tree a Makefile builds. Its top directory is its root. The
    commands on C-x p work on the project of the file you are editing,
    wherever in the tree the file is, as if you had gone to the root first:

        C-x p f         open a file of the project, by any part of its path
        C-x p r         open a file of the project you opened recently
        C-x p g         search every file of the project for a text
        C-x p G         search every file of the project for a regexp
        C-x p l         list the findings about the files of the project
        C-x p c         build at the root
        C-x p !         run a shell command at the root
        C-x p p         go to another project, and do one of these there
        C-x p b         go to another buffer of the project
        C-x p e         go to the project's shell, started at the root
        C-x p d         list the root, as dired does
        C-x p k         kill every buffer of the project

    Nothing moves: the directory of every buffer stays what it was, a
    file's buffer in its file's folder. The `files' page says what the
    directory of a buffer is.

    The modules these keys drive -- dired, grep, the build, M-!, the
    shell, the findings -- are loaded with the project's, so C-x p works
    whichever of them your init.lisp loads. Their own keys still work as
    they did, from the directory of the buffer you are in: M-s g searches
    from there, C-x p g from the root.

WHERE THE ROOT IS
    The root is found by looking upwards from the file of the current
    buffer -- or from the working directory, in a buffer with no file --
    for one of the names of `project-markers'. Out of the box they are,
    in this order:

        .git                            a Git repository
        .hg  .jj  .svn                  the other version control systems
        Cargo.toml  package.json        a build, of any of these kinds
        pyproject.toml  go.mod
        CMakeLists.txt  Makefile
        .project                        an empty file, to mark one by hand

    The first line that finds something decides, and within a line the
    nearest directory wins. So a .git wins over a nearer Cargo.toml: in a
    repository holding several crates, the project is the repository, not
    the crate. Outside any repository, the nearest build file is the root.

    Each entry of `project-markers' is a name or a list of names; a name
    may be a file or a directory. A .git that is a file, as in a worktree
    or a submodule, is a root as a .git directory is.

    The markers are looked for as `locate-dominating-file' looks for them,
    remembering what it found: after making or deleting one, call
    `locate-dominating-file-forget'. When the disk is slow to answer, the
    command says so and does nothing; it works when asked again.

A ROOT DECLARED BY HAND
    Where the markers give the wrong answer, say which directory is a
    root. M-x project-declare-root declares one for this run and the next
    ones; `project-roots', set in init.lisp, declares them in your
    configuration. A declared root wins over every marker for the files
    under it, and the nearest declared root wins over one further up.

    M-x project-forget takes a root declared with project-declare-root
    back; one in `project-roots' stays until you take it out of the list.

THE PROJECTS KNOWN
    A project is known once a C-x p command has run in it, or once it has
    been declared. The list is kept in the session, the newest first, so a
    project you worked on yesterday is still offered today: C-x p p asks
    for one, completing by any part of its path. A directory that is not
    in the list can be typed too. M-x project-forget takes a project out
    of the list, and `project-known-projects' returns it.

    Once the project is chosen, the echo area offers what to do there,
    one key each:

        rsedit: f find file g grep d dired e eshell b buffer ...

    and the key runs that C-x p command as if you were in the project:
    f is C-x p f, e goes to its shell, d lists its root. C-g or Escape
    does nothing, and any other key is not an answer. The keys are those
    of `project-switch-commands', a list of (KEY COMMAND LABEL); set it to
    a single command to run that one without asking:

        (setq project-switch-commands 'project-find-file)

THE BUFFERS OF A PROJECT
    A buffer belongs to the project its directory is in: a file's buffer
    to the project of its file, a dired listing to the one it lists, the
    output of C-x p c or C-x p ! to the root it ran at, a buffer made
    from a file of the project to that file's project. The editor's own
    buffers -- *scratch*, *log*, *Help*, a prompt -- belong to none:
    `project-buffer-ignore' names them.

    A buffer can also be claimed by a project, and then belongs to it
    wherever its directory goes. The project's shell is one: C-x p e
    goes to *NAME-eshell*, NAME being the last directory of the root,
    and starts a shell there at the root when none runs; after a cd in
    it to /tmp it is still the project's, and C-x p f from it still finds
    the files of the project. Its build is another: C-x p c runs in
    *NAME-compile*, so the builds of two projects keep their own output.
    `project-claim-buffer' claims any buffer by hand.

CLAIMING BUFFERS BY NAME
    M-x project-claim-mode, off when the editor starts, lets the projects
    claim buffers by their names as well. While it is on, a buffer with
    no file, made or renamed (M-x rename-buffer) in a buffer of a project,
    whose name one of `project-buffer-name-rules' matches, is claimed by
    that project and has its root as directory, wherever in the tree it
    was made from. The rules are regular expressions in which %p stands
    for the project's name. Out of the box the one rule claims every
    buffer whose name starts with *NAME-, so *rsedit-notes* made from any
    file of rsedit starts at its root. Turned on in init.lisp:

        (project-claim-mode 1)

    It costs nothing to the buffers whose names no rule could match,
    whatever the project: the name is looked at first, with %p standing
    for any name, and only a name that could be a project's makes the
    root be looked for on the disk. The editor's own buffers and the
    prompts are passed over before that. With the mode off, the rules are
    not read at all, and a buffer made in a project keeps the directory
    of the buffer it was made from.

    C-x p b asks for one of the other buffers of the project, by any part
    of its name. C-x p k asks once, with y or n, and kills them all;
    those with unsaved changes are asked about once more, together, and a
    no keeps them. `project-buffers' returns their names, and
    `project-buffer-p' says whether one is of a project.

FINDING A FILE
    C-x p f asks for a file, with the paths relative to the root to choose
    from. It leaves out what C-x C-r leaves out: the directories of
    `find-file-recursive-ignore', what the .gitignore files say, and the
    files past `find-file-recursive-limit'. The `dired' page has them. The
    list is the index of the tree (see the `files' page): the prompt opens
    at once, and Tab offers more while the tree is still being walked.

    C-x p r asks for one of the files M-g r would offer, those under the
    root only, newest first and written from the root: the `session' page
    has the recent files.

WORKING AT THE ROOT
    C-x p g asks for a text and lists the lines that contain it, in every
    file under the root, as M-s g does under the working directory; C-x p
    G asks for a regular expression instead, as M-x grep-regexp does. The
    `searching' page has the list and M-g n.

    C-x p l lists the findings -- what the compilers, the linters and the
    language servers said -- about every file under the root, as M-x
    findings-list-under would for the root, the files named from it; M-g
    n walks them. The `findings' page has the list.

    C-x p c asks for a command and runs it at the root as C-c c would, in
    the project's own output, *NAME-compile*, and C-x p ! asks for a
    shell command and runs it there as M-! would. The output keeps the
    root as its directory, so g in a build's output builds there again,
    in the same buffer, and the places a build names are read from the
    root. The `compile' and `shell' pages have the output.

    project-compile-command runs a command it is given rather than one it
    asks for, at the root, and returns t; outside a project it says so and
    returns nil. The Build, Test and Run entries of the menus of the
    languages call it, as Rust's Build runs cargo build: the `menus' page.

    Each of these prompts keeps its own history: C-p at the prompt gives
    back what you asked for last, in any project.

DOING SOMETHING IN ANOTHER PROJECT
    `project-with-root' calls a function as if the project at a root were
    the current one, wherever you are: `project-root' answers that root,
    and it is the directory the function runs in. It is how C-x p p runs
    its commands, and works the same way for one of yours:

        (project-with-root "~/src/app/" 'project-eshell)

    A prompt opened inside is answered after the function has returned:
    the C-x p commands keep the root for the answer, as C-x p g searches
    there, but a command of another module that asks first, as M-s g
    does, runs its answer in the directory of the buffer you are in.

EXAMPLES
    Claim buffers by name, those named *notes: NAME* as well:

        (project-claim-mode 1)
        (setq project-buffer-name-rules
              '("^\\*%p-" "^\\*notes: %p\\*$"))

    Offer only three things to do in the project C-x p p chooses, and
    go straight to its shell with s:

        (setq project-switch-commands
              '(("f" project-find-file "find file")
                ("g" project-grep "grep")
                ("s" project-eshell "shell")))

    Make a directory with a WORKSPACE file a root, before the others:

        (setq project-markers (cons "WORKSPACE" project-markers))

    Let only version control mark a root, never a build file:

        (setq project-markers '(".git" (".hg" ".jj" ".svn")))

    A monorepo whose subdirectories are projects of their own, though the
    whole is one repository:

        (setq project-roots '("~/src/mono/server" "~/src/mono/client"))

    The root of the current file, from Lisp, or nil:

        (let ((root (project-root)))
          (if (stringp root) root nil))

    Build with make at the root of the project, from a key of your own:

        (defcommand my-make () nil
          "Run make -k at the root of the current project."
          (let ((root (project-root)))
            (if (stringp root)
                (with-directory root (lambda () (compile "make -k")))
                (message "Not in a project"))))
        (define-key nil "C-c m" 'my-make)

    The same in one line, the message included:

        (define-key nil "C-c m" '(project-compile-command "make -k"))

LIMITS
    A repository around your home directory, as some keep for their
    configuration files, is the project of every file under it that is in
    no other repository: declare the roots you want with
    project-declare-root, or take ".git" out of `project-markers'.

    The root is found again, from the disk's remembered answers, each time
    a command runs: it follows the buffer you are in, and there is no
    current project apart from it. C-x p b and C-x p k find the project
    of each buffer the same way.

    A buffer belongs to one project: in a repository holding a declared
    root, a file under that root is of the inner project only.
