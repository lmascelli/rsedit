  Fixed in the *syntax table*, not in electric-pair -- the third bug of that
  shape, after block comments and character literals, and always the same
  cause: the grammar knows a construct that the table does not.

  electric-pair refuses to add a closer when the buffer already balances, so
  it is only ever as right as the scanner's answer to "does this balance". In
  =core/src/editor.rs= the answer was wrong. =create_global_env= holds the
  default init.lisp in a raw string, and one of its comments reads
  =; typing "(" gives you "()"=. The scanner knew only the =string= syntax
  class -- one character that opens and the same one that closes -- so it read
  =r#"..."#= as a run of ordinary strings with *code* between them. That =(=
  became a real open bracket, the whole file reported depth 1 instead of 0,
  and from there electric-pair paired everywhere in it. The closer it offered
  was the brace already closing the body, which is why deleting the stray one
  took the opener with it.

  The table now carries string *styles* with literal delimiters, declared per
  mode with =set-string-syntax=; rust-mode declares =r#"= / ="#=, =br#"=,
  =r"= and =br"=. The longest opener wins, so a raw-string opener beats the
  plain quote it begins with, and nothing is escaped inside one -- a raw
  string exists so a backslash is a backslash. Everything that reads the table
  is fixed at once: =forward-sexp=, the indenter, =syntax-ppss=.

  =core/src/tests/raw_string_tests.rs= pins it, including the reported
  scenario and a regression that opens this editor's own sources and asserts
  they balance -- the test that would have caught all three of these bugs.

- [X] Cache the syntax table's scan, so that reading the buffer as balanced
      expressions does not start at character zero every time.

  Every scan -- `forward-sexp', `up-list', the indenter, `syntax-ppss',
  electric-pair -- began at the top of the buffer, because the top was the only
  offset whose state the scanner knew without being told. So the cost of asking
  anything about point was the distance from the start of the file to point,
  paid again on every keystroke. `Scan::begin' had said for a while that this
  was where the fix went and that the colouring cache next door showed how.

  It is a second cache, not a share of the first. The grammar and the syntax
  table are two different lexers answering two different questions, and the
  colouring cache's state is a stack of open *regions*, which no motion can be
  answered from.

  `ScanCache' keeps one snapshot every 64 lines rather than a state per line:
  a scan state carries the positions of the lists it is inside, so two lines at
  the same depth still differ and the interning the colouring cache relies on
  would dedupe nothing. `Scan::begin' takes the nearest snapshot at or before
  the position asked about, and ignores anything else -- a snapshot is a
  shortcut to a position, never a substitute for reaching it, so a stale or
  ill-fitting one costs a full scan rather than a wrong answer.

  Filling it is the background worker's job (`modes/prescan.rs'), beside the
  highlighter and on the same timer. Readers only ever read, which is what keeps
  them on the read lock they already hold instead of needing the buffer's write
  lock, on the keystroke path, to make a performance cache work.

  An edit on line L cannot change the text above L, so every snapshot entering a
  line at or before L survives it and the rest are dropped. That is the whole
  bookkeeping: none of the line-shift accounting the colouring cache's header
  says is missing, because the snapshots kept are exactly the ones that did not
  move.

  Measured in the perf suite (SEXP SCAN): asking for the context deep inside a
  10,000-line file went from 131 ms to 0.42 ms, and asking at the bottom now
  costs 1.02x what asking halfway down costs -- the price of a motion no longer
  depends on where in the file it is asked.

  Two things deliberately left: `backward-sexp' never resumes, because a
  snapshot carries the shape of the open lists but not the expressions already
  passed inside them, and those are exactly what it reads. And the whole-buffer
  balance check electric-pair makes still scans from the edit to the end of the
  file, because that tail is what the keystroke changed -- see the note below.
